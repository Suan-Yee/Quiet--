# Quiet authentication backend

Authentication-only foundation for Quiet using Go 1.24, Gin, GORM, PostgreSQL, Redis, JWT access/refresh tokens, `golang-migrate`, Docker Compose, and pgAdmin.

Posts, comments, reactions, bookmarks, notifications, subscriptions, groups, and chat are intentionally not implemented.

## Frontend-derived user contract

The model was selected after inspecting the React login, signup, profile, navbar, post-card, article-preview, local-auth, mock-user, and shared TypeScript user files.

- Signup currently supplies `name`, `email`, `password`, and `confirmPassword`; the backend derives a unique username.
- Login uses email and password.
- Existing UI identity fields are name, username, email, profile image, cover image, bio, short author description, role, active state, and timestamps.
- Profile topics, cadence, readers/following counts, and social relationships remain outside the user table.

The database uses UUID primary keys as required by the backend specification. API IDs are therefore JSON strings; the frontend's numeric mock ID types will need to become strings when it is connected to this API.

## User schema

| Field | Reason |
| --- | --- |
| `id` | PostgreSQL UUID generated by `gen_random_uuid()` |
| `name` | Signup/display name used throughout the frontend |
| `username` | Unique profile identity derived from name; explicitly supplied by the admin seed |
| `email` | Unique normalized login identifier |
| `password_hash` | Bcrypt credential, never returned |
| `profile_image` / `cover_image` | Existing frontend image fields |
| `bio` / `author_description` | Long profile text and short post byline |
| `role` | Validated `user` or `admin` value |
| `is_active` | Account disablement without deleting identity |
| timestamps | Time-zone-aware creation/update times |

Schema changes are versioned SQL migrations in `migrations/`. GORM is used only for normal repository queries; the application does not call `AutoMigrate`.

## API

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/health` | Process liveness |
| `GET` | `/ready` | PostgreSQL and Redis readiness |
| `POST` | `/api/v1/auth/signup` | Register a normal user and issue tokens |
| `POST` | `/api/v1/auth/login` | Email/password login |
| `POST` | `/api/v1/auth/refresh` | Rotate the refresh session and token pair |
| `POST` | `/api/v1/auth/logout` | Revoke a refresh session; already-revoked sessions still succeed |
| `GET` | `/api/v1/auth/me` | Return the current user using a bearer access token |

Signup passwords must contain 8-72 bytes, an uppercase letter, a lowercase letter, and a number. Signup cannot select a role.

Successful authentication responses use this shape:

```json
{
  "success": true,
  "message": "Login successful",
  "data": {
    "user": {},
    "accessToken": "...",
    "refreshToken": "...",
    "tokenType": "Bearer",
    "accessExpiresAt": "...",
    "refreshExpiresAt": "..."
  }
}
```

Validation errors are field-oriented:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {
    "email": "A valid email is required"
  },
  "requestId": "..."
}
```

## Tokens and Redis sessions

Access and refresh JWTs use separate HMAC secrets and expirations. Both contain `sub`, `role`, `jti`, `iat`, and `exp`, plus an enforced token type. The access JWT also references its refresh-session ID.

Only the opaque refresh `jti` and associated user UUID are stored in Redis—not the raw token. Refresh rotation atomically creates the new session and removes the old one. Logout deletes the same Redis session, immediately invalidating both tokens in that pair.

## Docker Compose

Copy `.env.example` to `.env`, then replace both JWT placeholder values with independent random secrets:

```bash
docker compose up --build
```

Services:

- API: `http://localhost:8080`
- PostgreSQL: `localhost:5432`
- Redis: `localhost:6379`
- pgAdmin: `http://localhost:5050`

Local defaults are database `quiet`, user `quiet_user`, and password `quiet_password`. They are development-only and configurable through environment variables. Containers use `postgres` and `redis` service names rather than `localhost`.

PostgreSQL, Redis, and pgAdmin use named volumes. PostgreSQL and Redis have health checks, and the API waits for both to become healthy.

In pgAdmin, add a server using host `postgres`, port `5432`, and the configured Quiet database credentials.

## Initial admin seed

The API never embeds or logs an administrator password. Configure:

```dotenv
INITIAL_ADMIN_USERNAME=quietadmin
INITIAL_ADMIN_EMAIL=admin@quiet.local
INITIAL_ADMIN_PASSWORD=ChangeThisPassword123!
```

Run the idempotent seed locally:

```bash
go run ./cmd/seed
```

Or run the seed binary inside the Compose API image:

```bash
docker compose run --rm api /app/quiet-seed
```

It hashes the password with bcrypt, creates an admin only when absent, rejects collisions with normal accounts, and never prints the password.

## Local Go development

When the Go process runs outside Docker, change `DB_HOST` and `REDIS_HOST` from their Compose service names to `localhost`.

```bash
go run ./cmd/api
go test ./...
go vet ./...
```

Configuration validation fails startup when database/Redis settings or JWT secrets are missing, both JWT secrets match, placeholder secrets remain, refresh expiration is invalid, admin seed values are incomplete, or production CORS uses a wildcard.

Security middleware includes access-token authentication, an admin-role guard for future admin routes, request IDs, structured request logging without credentials or headers, panic recovery, centralized errors, a 1 MiB request-body limit, secure response headers, explicit-origin CORS, and Redis-backed login/signup rate limits.
